# 로그인·글쓰기 붙이기 — MCP 버전 (비개발자용)

[Supabase 따라하기 (MCP 버전)](Supabase-따라하기-MCP.md)까지 끝내면 **화면에 데이터가 보이는 것**까지 됩니다. 하지만 아직 데이터를 **넣는 건 Claude에게 부탁해야** 합니다.

이 문서의 목표는 **사이트 방문자가 직접 글을 쓰게** 만드는 것입니다. 다만 아무나 쓰면 안 되니 **GitHub으로 로그인한 사람만** 쓰게 합니다.

> **먼저 끝나 있어야 하는 것**: [Supabase 따라하기 (MCP 버전)](Supabase-따라하기-MCP.md)의 5단계까지 완료 — 사이트에 공지 목록이 보이는 상태.

---

## 이 문서에서 만드는 것

| 누구 | 읽기 | 쓰기 |
|------|------|------|
| 로그인 안 한 사람 | 가능 | 안 됨 |
| 로그인한 사람 | 가능 | **본인 글만** 쓰기·수정·삭제 |

"본인 글만"이 핵심입니다. 로그인만 했다고 남의 글을 고칠 수 있으면 안 됩니다.

전체 흐름은 4단계입니다.

```
0. GitHub 열쇠 만들기(수동) → 1. Supabase에 등록(수동) → 2. 표에 작성자 칸 추가 → 3. 화면 만들기 → 4. 확인
```

> **0·1단계만 손으로 합니다.** GitHub은 이 열쇠를 자동으로 만들어주는 기능을 제공하지 않습니다. 강사가 미리 만들어 두는 편이 낫습니다.

---

## 0단계 — GitHub 열쇠 만들기 (수동)

**먼저 우리 Supabase 주소를 확인해 둡니다.** 아래 표의 Callback URL에 이 주소가 들어가는데, 한 글자라도 다르면 로그인이 실패합니다. Claude Code 창에 이렇게 물어보세요.

```
우리 supabase 주소 알려줘
```

돌려주는 `https://○○○○.supabase.co`를 그대로 복사해 둡니다.

이제 <https://github.com/settings/developers> → **New OAuth App**으로 들어가 채웁니다.

| 입력칸 | 넣을 값 |
|--------|---------|
| Application name | 알아보기 쉬운 이름 (예: `1조 사이트`) |
| Homepage URL | 우리 사이트 주소 (`https://...vercel.app`) |
| Authorization callback URL | 방금 복사한 Supabase 주소 뒤에 `/auth/v1/callback` → `https://○○○○.supabase.co/auth/v1/callback` |

**Register application**을 누르면 **Client ID**가 나옵니다. 그 아래 **Generate a new client secret**을 눌러 **Client Secret**도 만듭니다.

> **Client Secret은 비밀번호입니다.** 채팅창·문서·코드에 붙여넣지 마세요. 아래 1단계에서 Supabase 화면에 바로 넣습니다. 실수로 노출했다면 같은 화면에서 **재발급(rotate)** 하면 됩니다.

---

## 1단계 — Supabase에 등록 (수동)

Supabase 대시보드 → 우리 프로젝트 → **Authentication → Sign In / Providers → GitHub**

1. **Enable Sign in with GitHub** 토글을 켭니다.
2. 0단계의 **Client ID**와 **Client Secret**을 붙여넣습니다.
3. **Save**를 누릅니다.

그리고 **Authentication → URL Configuration**으로 가서

4. **Site URL**에 우리 사이트 주소를 넣고 저장합니다.

```
https://우리프로젝트.vercel.app
```

> **Site URL을 빠뜨리면 로그인 후 `localhost:3000`으로 튕깁니다.** 가장 흔한 실패 지점입니다. 꼭 넣으세요.

### 제대로 켜졌는지 확인하기

Claude에게 이렇게 물어보면 실제로 확인해 줍니다.

```
우리 프로젝트에 github 로그인이 켜져 있는지 확인해줘
```

```
켜져 있습니다. GitHub 로그인 화면으로 정상 연결됩니다.
  client_id: Ov23li...
  돌아올 주소: .../auth/v1/callback
```

## 2단계 — 표에 "작성자" 칸 추가하기

지금 표에는 **누가 썼는지 적는 칸이 없습니다.** 그게 없으면 "본인 글만" 판단을 할 수 없습니다.

> **5교시를 [웹 버전](Supabase-따라하기.md)으로 한 팀은 먼저 읽어주세요.** 웹 버전은 표를 만들 때 **RLS를 끄고** 진행할 수 있습니다. 그 상태에서 아래처럼 쓰기 정책을 걸면 RLS가 다시 켜지는데, **읽기 정책이 없으면 목록이 통째로 사라집니다.** 그러니 아래 요청에 **"읽기 공개 정책도 같이 걸어줘"**를 반드시 덧붙이세요. [MCP 버전](Supabase-따라하기-MCP.md)으로 한 팀은 이미 읽기 정책이 있으니 그대로 진행하면 됩니다.

```
notices에 작성자 칸 추가하고,
로그인한 사람만 글을 쓸 수 있게,
자기가 쓴 글만 수정·삭제할 수 있게 정책 걸어줘.
읽기 공개 정책도 같이 걸어줘 (이미 있으면 그대로 두고).
```

```
작성자 칸(user_id)을 추가했습니다.
정책 3개를 추가했습니다.
  로그인한 사람만 작성
  본인 글만 수정
  본인 글만 삭제
읽기 공개 정책은 그대로입니다.
```

끝나면 **목록이 아직 보이는지 사이트를 새로고침해 확인하세요.** 목록이 사라졌다면 읽기 정책이 빠진 것입니다.

```
읽기 공개 정책이 걸려 있는지 확인하고, 없으면 걸어줘
```

이게 6교시의 실질적인 핵심입니다. 웹 화면에서 하면 정책을 세 개 따로 만들고 조건식을 손으로 써야 하는데, 한 문장으로 끝납니다.

## 3단계 — 화면 만들기

```
사이트에 GitHub 로그인 버튼과 공지 작성 폼 만들어줘.
로그인 안 하면 목록만 보이고,
로그인하면 제목·내용 입력칸이 나오게 해줘.
글을 쓰면 목록에 바로 보이게 해줘.
```

> **마지막 줄을 빼지 마세요.** 이게 빠지면 "글은 저장됐는데 목록에 안 나온다"는 6교시 최다 함정에 그대로 걸립니다. 왜 그런지는 아래 "가장 헷갈리는 함정"에서 설명합니다 — 미리 넣어두면 겪지 않습니다.

Claude가 코드를 만들고 무엇을 했는지 알려줍니다. 다 만들었으면 올립니다.

```
저장해줘
```

GitHub에 올라가면 Vercel이 자동으로 다시 배포합니다.

> **강사 포인트**: 이 단계에서 Claude가 **"목록을 매번 새로 불러오게 바꿨다"**는 설명을 할 수 있습니다. 위 마지막 줄 때문에 생긴 변경이며, 6교시의 핵심 개념입니다. 그냥 넘기지 마세요.

---

## 4단계 — 확인

1. 사이트를 새로고침합니다.
2. **GitHub으로 로그인**을 누르고 GitHub에서 **허용**합니다.
3. 돌아온 화면에서 제목·내용을 넣고 **공지 추가**를 누릅니다.
4. 방금 쓴 글이 **목록 맨 위에 바로 나타나면** 성공입니다.

제대로 저장됐는지 Claude에게 확인을 부탁할 수 있습니다.

```
방금 쓴 공지가 누구 이름으로 저장됐는지 확인해줘
```

```
id 6 / title "test"
작성자: heinemann9 (sinankng@gmail.com)
```

---

## 가장 헷갈리는 함정 — "글은 저장됐는데 목록에 안 나온다"

3단계에서 마지막 줄을 넣었다면 겪지 않지만, 왜 그런지는 알아둘 만합니다.

6교시에서 **가장 많이 막히는 지점**입니다. 증상이 이렇습니다.

- 글을 쓰면 "저장했습니다"가 나온다
- 그런데 목록에 안 보인다
- 새로고침해도 안 보인다
- Supabase에서 확인하면 **분명히 저장되어 있다**

원인은 권한이 아니라 **화면이 만들어지는 시점**입니다. Next.js는 기본적으로 **배포할 때 한 번 데이터를 읽어 화면을 미리 만들어 둡니다.** 그래서 그 뒤에 추가된 글은 다음 배포 때까지 안 보입니다.

고치는 방법은 "매번 새로 읽어라"고 지정하는 것입니다. Claude에게 이렇게 말하면 됩니다.

```
글을 쓰면 목록에 바로 보이게 해줘
```

> **강사 포인트**: 이 함정은 **기능이 정상인데 고장난 것처럼 보이는** 종류라 수강생이 자기 코드를 의심하며 시간을 버립니다. 3단계 안내 때 미리 짚어주세요. 배포 로그에서 `/`가 `Static`이면 이 문제이고, `Dynamic`이면 정상입니다.

## "본인 글만"이 정말 지켜지는지 확인해보기 (선택)

궁금하면 Claude에게 남의 글을 건드려 보라고 시킬 수 있습니다.

```
다른 사람 계정인 것처럼 해서 내 글을 수정·삭제해보고, 막히는지 확인해줘
```

```
남의 글 수정 → 0행 (차단)
남의 글 삭제 → 0행 (차단)
남의 이름으로 작성 → 오류 42501 (차단)
본인 글 수정 → 1행 (통과)
```

여기서 **중요한 차이**가 보입니다.

| 동작 | 막힐 때 나타나는 모습 |
|------|----------------------|
| 수정·삭제 | **에러 없이 "0건 처리"** — 조용히 아무 일도 안 일어남 |
| 작성 | **오류 메시지**(42501)가 뜸 |

수정·삭제는 에러가 안 나기 때문에, **"수정 버튼을 눌렀는데 아무 반응이 없다"가 정상 동작**일 수 있습니다. 고장이 아닙니다.

## 자주 막히는 곳 (체크리스트)

| 순서 | 증상 | 원인 · 이렇게 말하세요 |
|------|------|------------------------|
| 1 | 로그인 후 `localhost:3000`으로 튕김 | **Site URL 미설정** — 1단계 4번 |
| 2 | GitHub에서 `redirect_uri mismatch` | Callback URL 오타 — 0단계 재확인 |
| 3 | 로그인 버튼을 눌러도 반응 없음 | `github 로그인이 켜져 있는지 확인해줘` |
| 4 | 저장은 되는데 목록에 안 나옴 | **위 "가장 헷갈리는 함정"** — `글을 쓰면 목록에 바로 보이게 해줘` |
| 4-1 | 2단계 뒤로 목록이 통째로 사라짐 | **읽기 정책 누락**(웹 버전으로 5교시를 한 팀) — `읽기 공개 정책이 걸려 있는지 확인하고, 없으면 걸어줘` |
| 5 | 저장 시 `42501` 오류 | 작성자 칸·정책 누락 — `쓰기 정책 확인해줘` |
| 6 | 글 번호가 건너뜀 (3 → 6) | **정상입니다.** 실패한 시도도 번호를 소비합니다 |
| 7 | 남의 글이 수정됨 | 정책이 잘못 걸린 것 — `본인 글만 수정되게 정책 다시 확인해줘` |

6번을 미리 알려주세요. 수강생이 "번호가 왜 뛰어요?"라고 자주 묻습니다.

## 안전하게 쓰기

- **Client Secret을 채팅·코드·문서에 넣지 않기.** Supabase 화면에 직접 넣습니다. 노출됐다면 GitHub에서 재발급.
- **읽기 공개는 그대로 두되, 개인정보를 넣지 않기.** 이 표는 누구나 읽을 수 있습니다. 전화번호·주소 같은 것을 넣으면 안 됩니다.
- **"모두 삭제해줘" 같은 말은 신중하게.** Claude는 실제로 지울 수 있습니다.

## 강사 메모

- 본 문서는 [Curriculum.md](Curriculum.md) **6교시(핵심 기능 붙이기)** 에 대응합니다. 4·5교시는 [Supabase 따라하기 (MCP 버전)](Supabase-따라하기-MCP.md), 2·3교시는 [Vercel 배포 따라하기 (MCP 버전)](Vercel-배포-따라하기-MCP.md).
- **0·1단계는 강사 사전 준비로 빼는 것을 강력히 권합니다.** GitHub OAuth App 생성은 자동화가 불가능하고(GitHub이 API를 제공하지 않음), Callback URL·Site URL 오타가 팀별로 반복 발생합니다. 8개 팀 것을 미리 만들어 Client ID/Secret을 팀별로 전달하는 편이 빠릅니다.
- **진도 차가 가장 벌어지는 교시**입니다. 커리큘럼 지침대로 느린 팀은 [Supabase 따라하기 (MCP 버전)](Supabase-따라하기-MCP.md) 5단계(조회만)까지로 마감하고, 본 문서는 빠른 팀 확장 과제로 돌리는 운영이 현실적입니다.
- **"저장은 됐는데 목록에 안 나온다"를 반드시 사전 설명하세요.** 실측 확인된 함정입니다. 정적 프리렌더 상태에서는 새 글이 다음 배포까지 안 보이며, 수강생은 권한 문제로 오진합니다. 배포 로그의 `/` 항목이 `Static`인지 `Dynamic`인지가 판별 기준입니다.
- **수정·삭제 차단은 에러가 아니라 0행**입니다. insert만 42501을 던집니다. 이 비대칭을 모르면 "차단이 안 되는 것 같다"고 오판합니다.
- 본 문서의 모든 단계는 실제 프로젝트에서 검증했습니다(2026-08-17). GitHub OAuth 연결, 로그인 후 작성(작성자 UUID 기록), 남의 글 수정·삭제 차단(0행), 남의 이름으로 작성 차단(42501), 새 글 즉시 반영이 모두 실측 결과입니다.
- 정책의 조건식에는 `(select auth.uid())` 형태를 쓰도록 안내되어 있습니다. 행마다 재평가되지 않아 데이터가 많아질 때 속도 차이가 납니다. 정책에 쓰는 칸(`user_id`)에는 인덱스도 함께 만듭니다.
